#### 1.1 revision 三处语义（主理人裁决 2：脚本断言分别命名、不得混用）

| 位置 | 名称 | 语义 | 脚本中的取法 |
| --- | --- | --- | --- |
| 事件 `revision` / 对象 `applied_revision` | **业务 `system_revision`** | 业务库全局单调版本，版本顺序与去重依据 | `GET /api/revision` → `_base_revision(c)`；注入事件用它构造 `R` / `R-1` |
| `GET /api/ontology/revision` 的 `revision` | **`ont_platform_revision`** | 底座平台版本，仅前端短轮询用；重建也 bump、只增不减 | `revision_contract` / `rebuild_consistency` / `crash-after` 单独断言 |
| `/sources/status` 的 `snapshotRevision` / `currentSourceRevision` | **业务 `system_revision` 水位** | 快照水位与源当前水位 | `source_status_contract` / `revision_contract` 断言 `snapshot <= current` 且 `current == 业务 revision` |

> 三者是不同计数器：**不得**用 `ont_platform_revision` 比较事件新旧，也**不得**把业务 revision 当作前端短轮询版本。
> 工程师口径（v1.2）：版本顺序比较**严格**为「事件 `revision` vs 对象 `applied_revision`」，两者都取业务 `system_revision`；**绝不能用** `ont_platform_revision` 参与比较。脚本注入事件一律用 `_base_revision(c)`（业务 `/api/revision`），`verify_revision_contract` 只校验三处语义分离、不做跨计数器数值比较。

### 2.3 验收三：同步正确性（6 种情况，逐条可独立调用、可重复执行）

| # | 测试项 | 前置条件 | 可复现命令 | 通过标准 |
| --- | --- | --- | --- | --- |
| ① | 同一 eventId 重复投递 | **裁决 1**：`/internal/events` 允许故障注入、不校验 `eventId` 是否存在于业务 Outbox；直接 POST 构造事件，**不加「先查 outbox」前置**；事件须带 `payload.sourceTable/sourcePk` | `python tests/ontology_acceptance.py --case sync_dup_event` | 断言构造事件带 `sourceTable/sourcePk`；首次 `ack=true,persisted=true`（不达即源码缺陷，不再 `skipped`）；第 2/3 次 `ack=true / DUPLICATE`（`persisted` 非 true，兼容 `skipped/status/message` 中的标记）；`/changes` 总数最多 +1；同一 `eventId` ≤1 条变化；对象/关系数稳定；**收尾自动 reset 恢复源/投影一致** |
| ② | 较旧 revision 晚于新事件到达 | 同上（裁决 1）；事件 revision 用**业务 `system_revision`**；**两条事件都必须带 `payload.sourceTable`/`sourcePk` 且解析出同一个 globalId**（否则会被当成「无对象变化」仅 bump 平台版本，导致**假通过**） | `python tests/ontology_acceptance.py --case sync_stale_event` | 断言 hi/lo 同源且 `hi.revision > lo.revision`（均为业务 revision）；hi **确实改变了对象投影**（出现陈思琪/15:30，非仅 bump 版本）；lo 返回 `ack=true / STALE` 且不落库；最终仍为「陈思琪 / 15:30」（**不回退**）；旧事件未追加伪造历史；收尾自动 reset |
| ③ | 同步中途失败与重启 | **[人工·主理人]** 消费处理到一半强制终止并重启本体服务 | 终止前：`--phase crash-before`；重启后：`--phase crash-after` | 前半段记录业务 revision / 变更数 / `ont_platform_revision` / 待处理数基线；后半段重启追赶完成后：同一 `eventId` 无重复、底座变化数不减（无遗漏）、无未恢复失败/死信、`ont_platform_revision` 不回退；缺基线则 `skipped` |
| ③补 | 底座 `/admin/retry` 重放失败事件 | **工程师口径**：端点已改为**代理转发**业务侧 `POST http://backend:8080/admin/retry?eventId=`（业务侧同时支持 `/api/admin/retry` 与 `/admin/retry`）；脚本**只调底座端点** | `python tests/ontology_acceptance.py --case admin_retry` | 成功路径：`{eventId, status:"PENDING", attempts:0, message:"已重新排队"}`、重放收敛、同一 `eventId` 最多 1 条变化、无遗留 `DEAD`；**来源不可用路径**：`sourceUp=false` 时返回 `SOURCE_UNAVAILABLE` + 中文错误（复用「停原业务服务」停机窗口，未停服务则 `skipped`） |
| ④ | 全量导入期间发生业务修改 | 本体服务在线；导入端点可用 | `python tests/ontology_acceptance.py --case sync_import_during_change` | 启动 `/import/full` 后立即发起一次 `adjust`；导入结束后最终状态 = 最新业务状态（**不被旧快照覆盖**），本次变化记录**不遗漏**；连续两次导入对象数/关系数/`globalId` 不变；若导入过快未构成窗口，该子项 `skipped` 并写明，其余断言照常 |
| ⑤ | 对象删除后有效关系清理 | **裁决 1**：直接 POST 一条 `changeKind=DELETE` 事件构造删除场景，**无需人工直改库、无需查 Outbox**；payload 带 `sourceTable`+`sourcePk`+`tombstone` | `python tests/ontology_acceptance.py --case sync_delete_cleanup` | 脚本从 `/objects?type=lessonSession` 自动选一个非 LS-003 对象；断言 DELETE 事件带 `sourceTable/sourcePk/tombstone=true` 并被持久化（`ack=true,persisted=true`）；对象墓碑化 / 不再有效返回；其 `active=true` 关系数为 0（**无悬挂**）；有可解释变化记录；开头与结尾各 `rebuild` 一次保证可重复执行且不污染后续用例；**刻意不跑 reconcile**（源记录仍在，对账会把墓碑当 MISSING 修回） |
| ⑥ | 直改库后对账发现差异并修复 | **[人工·主理人]** 绕过业务服务直改库（见 §3 示例 SQL） | `python tests/ontology_acceptance.py --case sync_reconcile_fix` | 以「原业务 API 读到的当前值」为源真值：源/投影不一致时，`/reconcile` 列出 `FIELD_DIFF` 等差异并修复；修复后投影 = 源；`origin=RECONCILE` 历史 `operator=null`、`businessTime=null`、原因含「对账修复」（**不伪造操作人/发生时间/中间过程**）；第二次对账无新增差异（可重复执行）；未构造差异则 `skipped` |

> 「失败重试幂等」由 `admin_retry`（底座端点，裁决 4）、`after_recovery`（`DEAD=0`）与 `sync_import_during_change`（`/import/retry`）三处覆盖。

## 5. 「已实现能力 vs 未来扩展项」——本轮**不测试**的边界

依据 PRD §5、架构 §8 的措辞硬约束：**本轮只用 PostgreSQL 验证，真实接通数据源仅 1 个（学校业务库）**。以下仅列适配边界，**不实现、不测试、不宣称「已支持 / 已完成 / 已兼容」**。

| 类别 | 不测试的边界 | 理由 |
| --- | --- | --- |
| 数据库 | 达梦数据库（SQL 方言/DDL、JSONB 替代、`MERGE INTO` UPSERT、咨询锁、`FOR UPDATE SKIP LOCKED` 隔离级别、时间函数、JDBC 驱动、大小写/保留字） | 仅适配清单，本轮无实现无实测 |
| 数据源 | 其他 Java 业务系统接入、多数据源身份隔离（不同来源同主键/同名不合并） | 首版只接通 1 个来源；`globalId` 规则只做单源静态核验，不做跨源构造 |
| 基础设施 | 图数据库、搜索集群、Kafka / 复杂消息集群、完整权限治理平台 | PRD §5.3 明确不引入 |
| 建模 | 可视化建模器（C5，P2） | 首版界面可查看定义即可，不验收编辑器 |
| 前端 | 响应式深度交互（E8，P1） | 只做 390px 五页面 + 搜索 + 详情的**冒烟**（无横向溢出），不做完整可用性验收 |
| 内部实现 | `ont_*` 表结构、JSONB 列、索引、SQL UPSERT 语句、SSE 加速（可选 P1）、`pg_advisory_xact_lock` 并发 | 通过契约端点做黑盒验收，不白盒断言实现细节（除验收四的 git diff 源码零分支佐证） |
| 原业务新增 | `POST /api/schedule/batch-adjust`（本轮新增接口） | 不在既有 `tests/api_acceptance.py` 的 51 项内；本轮接口脚本不单独回归，建议工程师自测或后续补充；其 Outbox 覆盖由 `offline_writes` / 导入衔接间接观察 |

> 结果落盘与措辞必须遵守 PRD §5.1 三分法：只有「真实运行 + 真实执行 + 落盘结果」才可写「已实现并验证」；`skipped` 项一律不得计入通过。
