# 新增对象类型接入指南（以 classroom 教室类型为例）

> 本文是「验收四：新增业务对象类型时，通用内核与 ontology-web 前端零专用分支、零改动」的
> 操作手册与证据留档。批次④ 用 `classroom` 真实验证了一次完整接入：**只改 3 份 YAML + 新增 1 个
> 适配层 Provider**，`core / repository / controller / common / config` 五个包与
> `ontology-web/src/**` 一行未动。

---

## 1. 为什么可以「不改代码就加类型」

内核是**模型驱动**的，运行时行为全部由 `ontology-service/src/main/resources/ontology/` 下的三份
YAML 描述，Java 侧只保留两类东西：

| 层 | 内容 | 新增类型时是否需要改 |
| --- | --- | --- |
| 模型定义（YAML） | 有哪些对象、哪些属性怎么映射、有哪些关系怎么生成 | **需要改**（数据） |
| 适配层（`adapter/school/**`） | 学校领域特有的「只读联表查询 / 按查询时间算动态结果」 | 仅当新类型需要新的派生/动态能力时才加 |
| 通用内核（`core/**`） | 读定义、建快照、写投影、事件消费、对账、重建、查询 | **不需要改** |
| 接口层（`controller/**`）、仓储（`repository/**`）、通用前端（`ontology-web/src/**`） | 按模型元数据驱动的列表/详情/关系图/变更页 | **不需要改** |

关键机制：

1. **类型注册表**：`ModelRegistry` 把对象类型、关系类型、来源映射放进 `Map`，一切查询都是
   `map.get(id)`；`hasType / typeBySourceTable` 也是查表，不存在「认识哪些业务类型」的清单。
2. **扩展点策略表**：`SpiRegistry` 在启动时收集全部 `FieldMapping / RelationRule /
   DerivedPropertyProvider / DynamicResolver` Bean，按 `key()` 建索引；关系规则再按
   `generation.kind`（`FOREIGN_KEY` / `JOIN_RULE`）二次映射。运行期只有 `map.get(key)`，没有
   `switch (objectType)`。
3. **启动即校验**：`ModelDefinitionLoader` 与 `SpiRegistry` 在构造期做全量强校验（身份规则、
   属性类型枚举、`listFields/searchableFields` 必须是已定义属性、关系两端类型必须存在、
   YAML 声明的每个 provider/resolver key 必须有 Bean 实现）。任一不满足 → **服务拒绝启动**，
   不会出现「元数据配了但没人用」的空壳。
4. **前端零类型化**：`ontology-web` 的导航、属性表、列表列、关系图、变更页全部由
   `GET /api/ontology/model/types`、`/model/relations` 的返回渲染，`v-for` 生成，代码里没有
   `if (type === 'class')` 这类分支。

## 2. 接入步骤（照抄即可）

设新类型为 `X`，来源表为 `t_x`。

### 步骤 1：`ontology/model/object-types.yaml` 增加对象类型

```yaml
  - id: X                        # 全局唯一、正则 [A-Za-z_][A-Za-z0-9_]*，出现在 globalId 中
    displayName: 中文名           # 前端导航/标题直接用
    description: 一句话说明来源与业务含义
    identity:
      sourceId: school-panorama  # 必须等于 school-source.yaml 的 dataSource.id（跨源会串身份）
      sourceTable: t_x           # 来源表，用于事件解析反查类型
      sourcePk: id               # 来源主键列
      globalIdRule: "gid:{sourceId}:{objectType}:{sourcePk}"   # 固定写法，写错启动报错
    titleTemplate: "{name}"      # {字段} 占位，渲染时用属性值填充
    listFields: [code, name]             # 列表展示列，必须是已定义属性/派生属性
    searchableFields: [code, name]       # 关键字搜索命中列，同上
    filterableFields: [roomType]         # 前端筛选下拉项
    attributes:
      - { name: code,       type: string, displayName: 编号, required: true, unique: true }
      - { name: name,       type: string, displayName: 名称, required: true }
      - { name: capacity,   type: int,    displayName: 容量 }
      # from: "外键列.目标列" 表示属性由适配层联表取名（渲染侧视为「映射得到」）
      - { name: schoolName, type: string, displayName: 所属学校, from: "school_id.name" }
    derivedProperties: []        # 需要 Java 计算的属性写在这里，见步骤 4
    dynamicResolvers: []         # 依赖「查询时间」的实时结果，不落库
    sourceMappingRef: school-source.yaml#X    # 仅作文档引用
```

属性 `type` 允许枚举：`string / int / decimal / boolean / date / time / string[]`。
注意 `string[]` 在 flow mapping 中**必须加引号**（`type: "string[]"`），否则 `[` 会被 YAML
当成数组起始符。

### 步骤 2：`ontology/model/relation-types.yaml` 增加关系类型

外键直连（最常见）：

```yaml
  - id: X_in_school
    displayName: X 所属学校
    fromType: X                 # 必须是已注册对象类型
    toType: school
    forwardName: 所属学校        # 正向展示名（详情页「正向关系」）
    reverseName: 校内X           # 反向展示名（对端详情页可见，无需另建关系）
    direction: OUT
    cardinality: "N:1"
    businessEffectiveTime: false # true 时必须给 validFromColumns
    generation:
      kind: FOREIGN_KEY
      sourceTable: t_x
      fkColumn: school_id
      targetTable: schools
    sourceMappingRef: school-source.yaml#X
```

带业务有效时间的关系（例如「某天某节课才成立」）追加
`validFromColumns: [lesson_date, start_time]`——内核不认识「课表」概念，有效时间完全由定义列推导。

联表派生关系用 `kind: JOIN_RULE` + `sourceColumn / joinTable / joinFilterColumn /
joinSelectColumn`，不写 SQL。

### 步骤 3：`ontology/mapping/school-source.yaml` 增加对象映射

```yaml
objectMappings:
  X:
    sourceTable: t_x
    pk: id
    fieldMappings:
      # 直连：source 到 target
      - { target: code,     source: code }
      - { target: roomType, source: room_type }
      # 联表取名（策略表键 LOOKUP_NAME，内核不拼 SQL）
      - { target: schoolName, source: school_id, transform: LOOKUP_NAME,
          lookup: { table: schools, nameColumn: name } }
      # 嵌套联表（策略表键 NESTED_LOOKUP_NAME）
      # - { target: schoolName, source: class_id, transform: NESTED_LOOKUP_NAME,
      #     lookup: { table: classes, joinColumn: school_id, nameTable: schools, nameColumn: name } }
      # 日期/时间格式化（策略表键 DATE_yyyyMMdd / TIME_HHmm）
      # - { target: lessonDate, source: lesson_date, transform: DATE_yyyyMMdd }
    stableId: { rule: "gid:{sourceId}:{objectType}:{sourcePk}" }
    relationRules:
      - { relationType: X_in_school, fk: school_id, targetObjectType: school }
      # 需要业务有效时间时追加 validFromColumns: [lesson_date, start_time]
    joinRelationRules: []
    derivedProperties:
      - { name: sessionCount, provider: classroomUsageProvider, inputs: [id] }
```

字段含义：

- `sourceTable/pk`：快照分页扫描与事件回读用；`pk` 也是 `globalId` 最后一段。
- `fieldMappings[].transform`：**必须**是已注册的 `FieldMapping.key()`；当前内置
  `LOOKUP_NAME`、`NESTED_LOOKUP_NAME`、`DATE_yyyyMMdd`、`TIME_HHmm`。
- `relationRules[].fk`：来源表上的外键列；`targetObjectType` 决定关系另一端。
- `derivedProperties[].inputs`：给实现看的输入列清单（约定文档化，不做运行期强校验）。

### 步骤 4（仅当需要 Java 计算时）：新增 Provider / Resolver

- **派生属性**（快照期算一次、随投影落库）：实现
  `com.school.ontology.core.spi.DerivedPropertyProvider`，`@Component` 注解，`key()` 返回
  YAML 中引用的 key，`compute(rec, def, ctx)` 里只用 `ctx.lookups()` 的只读能力
  （`name / foreignKey / joinKeys / count / row`）。
- **动态结果**（按查询时间实时算、不落库不缓存）：实现
  `com.school.ontology.core.spi.DynamicResolver`，必须返回带可读 `basis` 的结果，
  可选 `aliases()` 声明别名（如 `nextLesson`）。

> 只有「需要新的 Java 计算」时才落到 `adapter/school/**`。`classroom` 本次只加了一个
> `ClassroomUsageProvider`，`core/**` 完全没动。

### 步骤 5：在 `school-source.yaml` 末尾登记 SPI

```yaml
providers:
  - { key: classroomUsageProvider, impl: com.school.ontology.adapter.school.provider.ClassroomUsageProvider }
```

未登记 → `SpiRegistry` 启动校验失败；登记了但 key 与 `@Component` 实现的 `key()` 不一致 →
同样启动失败（双向校验）。

### 步骤 6：验证

```bash
cd ontology-service && mvn -q clean package          # 定义校验在构造期执行，配置错即失败
cd ../ontology-web && npm run typecheck              # 前端不感知新类型，只需确认未被影响
```

服务启动后无需任何额外操作：`GET /api/ontology/model/types` 会多出一项，导航/列表/详情/关系图
自动出现新类型；对已有投影执行一次「全量导入」或「重建」，新类型的对象与关系即落库。

## 4. 两类时间：新增类型时最容易踩的坑

派生属性（`derivedProperties` + provider）会在**快照期算出来并落库**，因此**不能包含可变时间语义**：

- ❌ `todaySessionCount`（「今天」的排课数）：今天会随演示时间/真实日期变化，重建后与首次导入
  不一致，等于把时间语义混进投影，破坏「重建可复现」与两类时间分离。
- ✅ `sessionCount` / `usedPeriods`：只依赖静态外键关联，重建结果可复现。
- ✅ 「此刻正在上什么课」这类问题交给**动态 Resolver**（`dynamicResolvers` + `resolver`）：
  以 `queryTime` 为唯一时间源，实时计算、不落库、不缓存，且必须带可读 `basis`。

同理，`origin` 为 `RECONCILE` 的变更记录不得伪造 `operator` 与 `business_time`；
重建只清空 4 张投影表（`ont_object / ont_relation / ont_source_ref / ont_object_version`），
审计历史全保留，`ont_platform_revision` 只增不减。

## 5. 常见错误与对应报错

| 现象 | 原因 |
| --- | --- |
| 启动抛 `本体模型定义非法，服务拒绝启动：对象类型[X] 的可搜索字段 foo 不是已定义属性/派生属性` | `searchableFields/listFields` 写了未定义属性 |
| `... 的 globalIdRule 必须是 gid:{sourceId}:{objectType}:{sourcePk}` | 全局 ID 规则被改写（禁止自定义，防跨源串号） |
| `... 的 identity.sourceId 与 dataSource.id 不一致（跨源身份会串）` | `sourceId` 写错 |
| `关系类型[R] 的起止类型未注册` | `fromType/toType` 拼错或对象类型未定义 |
| `扩展点注册不完整，服务拒绝启动：Provider 未注册：xxxProvider` | `school-source.yaml` 的 `providers` 未登记或 `key()` 不一致 |
| `YAML` 解析报 `expected ',' or '}'` | flow mapping 里写了 `type: string[]`，需加引号 `"string[]"` |
