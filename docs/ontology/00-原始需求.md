## 一、项目目标

我要验证的是：**在一个已有业务系统之外，增加独立的本体数据底座，将原系统的数据映射为统一的业务对象和关系，提供跨对象查询、关系探索、变化追踪和全景展示。**

请把当前学校项目视为“已经存在的业务系统”。保留它的业务数据库、业务接口、操作入口和校验逻辑，以它作为第一个接入的数据源。

新增的平台应当有独立的服务、数据库和访问入口。学校是本平台的第一个接入案例，通用内核应当能够继续接入其他业务领域。

真实项目可能使用 Java 和达梦数据库。本轮使用现有 Java 技术栈和 Docker 中的 PostgreSQL 完成验证。设计清楚数据源适配边界，列出未来接入达梦需要验证的部分，不宣称已经完成未经测试的达梦支持。

先阅读当前代码、AGENTS.md 和 API 契约，给出简短实施计划，然后继续完成实现与测试。同步更新与新架构相关的文档和约束。

## 二、必须形成的架构

### 1. 原业务系统

继续负责业务操作、业务校验和事务。

原业务数据库是业务事实的权威来源。调课等操作仍通过原业务服务完成。

允许为接入底座增加必要的事件记录、适配接口和异步投递模块，但业务处理不能同步依赖本体平台可用。

### 2. 本体数据底座

新增可独立运行的后端服务，使用独立 PostgreSQL 数据库、连接配置和持久化存储。

底座至少保存：

- 本体模型：对象类型、属性定义、关系类型。
- 接入配置：数据源、来源映射、映射版本。
- 当前数据：对象实例、关系实例、来源引用、对象版本。
- 运行记录：变更历史、同步任务、消费进度和错误记录。

底座中的当前对象和关系属于可重建的数据投影，不能形成另一套相互竞争的业务事实源。

### 3. 展示应用

保留“原业务系统”入口，新增“本体平台”入口。

本体平台的对象查询、关系探索、总览和历史页面，统一调用本体服务 API。原业务停止服务时，平台仍能查询已经同步的数据，并明确显示数据的新鲜度。

平台如提供业务操作按钮，应跳转至原业务页面，或调用原有业务接口，沿用原有校验；不能直接修改底座投影来冒充业务操作成功。

## 三、本体模型必须真正驱动运行时

请实现以下定义与实例的区分。

### 对象类型定义

至少包括：

- 类型标识、显示名称、说明。
- 稳定的对象身份规则。
- 属性名称、数据类型、展示名称、必要的校验规则。
- 默认标题、列表字段、可搜索和可筛选字段。
- 数据来源映射。
- 必要的派生属性或计算器引用。

对象全局 ID 与来源主键分开设计。不同数据源中的相同主键、相同名称不能自动合并成同一对象。

### 关系类型定义

至少包括：

- 关系标识、名称、起点类型、终点类型。
- 正向和反向展示名称。
- 方向、基数及必要的业务有效时间。
- 关系生成规则和来源映射。

关系实例要能说明：连接了哪两个对象、为什么存在、来自哪条原始记录、由哪个映射版本生成。

### 来源映射

至少支持：

- 一张来源表映射为一种对象。
- 字段映射、简单转换和稳定 ID 生成。
- 根据外键生成关系。
- 通过联表或明确的计算规则生成派生属性、关系。
- 通过有明确接口的 Java Provider / Resolver 承载复杂业务逻辑。

首版允许使用 YAML、JSON 或 Java 注册定义，并提供校验、加载和版本记录。界面可以先查看定义，不强制开发完整可视化建模器。

**接入、实例生成、查询和前端展示必须实际使用这些定义。** 不能只创建几张“本体元数据表”，实际逻辑仍散落在学校、学生、老师专用的分支中。

学校领域代码应集中在独立的映射或适配模块。通用内核和通用前端不能通过不断增加业务类型的 `switch/if` 扩展功能。

## 四、学校数据的接入方式

首批接入学校、班级、学生、老师、课程和具体授课安排。

把“具体授课安排”作为独立对象，承载日期、时间、课程、老师、班级等关系。避免简单地把老师和学生直接连接后，丢失“哪一天、哪节课、什么角色”的信息。

明确区分：

- 来源中直接存在的属性和关系。
- 经过映射或计算得到的属性和关系。
- 依赖查询时间的动态结果。

例如“下一节课”需要通过关系和查询时间计算。即使没有任何数据库写入，时间跨过上课边界后，结果也应该变化。

这些计算应通过明确的领域扩展接口接入平台，并展示计算依据，不能散落在多个页面中重复实现。

**预留原数据库中已经存在的教室类型，作为后续扩展验收。** 先完成核心平台，再通过增加定义、映射及必要的适配器接入教室，证明通用搜索、详情和关系探索无需分别增加教室专用页面。

## 五、实现真实的数据同步闭环

### 1. 全量导入

支持首次导入、手动重跑、进度查看和失败重试。

重复导入不能产生重复对象和关系。设计并实现快照与增量衔接策略，保证导入期间发生的业务修改不会遗漏，也不会被旧快照覆盖。

支持从原业务数据重建底座的当前对象和关系。重建当前投影时，不能顺手删除平台已有的审计历史。

### 2. 增量同步

首版优先采用事务 Outbox：

- 原业务更新和 Outbox 事件写入同一个本地事务。
- 异步投递或消费事件，不能在业务事务内等待本体平台响应。
- 底座成功持久化后才确认处理成功。
- 事件具有唯一 ID，并携带足以还原变化的前后状态或等价信息。
- 处理去重、重试、版本顺序、删除和失败恢复。
- 一次业务变化对应的对象更新、关系更新、变更记录和平台版本，应保持一致。

不要求引入 Kafka。可以使用数据库轮询和轻量异步投递，但必须说明并测试如何避免漏事件、重复事件和旧事件覆盖新状态。

覆盖当前已有的相关写入口，包括调课、批量调整、重置及演示时间相关操作，不能只接通某一个按钮。

### 3. 对账与状态

增加可重复执行的对账机制，识别原业务与平台投影不一致的情况。

绕过业务服务直接修改数据库的行为，可由对账发现当前差异；对于没有捕获到的历史，不得伪造操作人、发生时间和中间过程。

清晰展示数据源状态、最后成功同步时间、处理进度、待处理数量、错误及重试结果。同步处理时间与演示业务时间分开记录。

## 六、完成可操作的平台界面

界面使用中文，至少包含以下五部分。

### 1. 全景总览

显示对象与关系规模、数据源状态、同步状态、近期变化及影响摘要。

提供全局搜索入口，用户可以直接找到具体对象，不需要沿学校、班级等层级逐级进入。

### 2. 通用对象探索器

根据类型定义动态生成类型列表、对象列表和详情。

对象详情至少包括：

- 当前属性和动态计算结果。
- 正向、反向关联对象。
- 最近变化。
- 来源系统、来源记录和映射信息。
- 返回原业务对象的入口。

支持筛选、分页和保留查询上下文。

### 3. 关系探索

同时提供关系列表和关系图。

支持以一个对象为中心展开一至两层关系，设置分页或节点数量上限。

点击关系能够解释它来自哪个字段、关联查询或计算规则。发生关系变化时，应能看到旧关系结束、新关系建立以及相关对象。

### 4. 变化与影响

展示属性前后差异、关系增加与解除、来源事件及时间。

从原对象和新对象两侧都能查到同一次关系变化。例如老师替换后，旧老师的历史中仍应保留这次变更。

明确区分“本身发生变化的对象”和“按规则计算出的相关对象”，显示影响判断的依据。不要把所有邻接对象都标成业务状态已经改变。

### 5. 模型与接入管理

能够查看对象类型、属性、关系类型、数据源、映射定义与版本。

提供全量导入、对账、同步任务查看和失败重试入口。

使用者应能区分“没有业务数据”“尚未接入”“同步落后”和“同步失败”。

## 七、必须实际完成的验收

### 验收一：跨系统变化

在原业务页面完成一次调课。

本体平台中已经打开的相关对象详情、关系列表、关系图和变化记录自动更新，旧老师与新老师两侧都能看到历史。

本地无故障环境下，从业务提交成功到已打开页面完成更新，目标不超过 5 秒。记录实际耗时和测试条件。

页面刷新失败后必须重试，不能因为提前记住了新版本号而永久停留在旧数据。

### 验收二：独立运行与恢复

停止本体服务，原业务仍能完成多次合法修改。

恢复本体服务后自动追赶，最终状态和变化记录正确。

停止原业务服务，本体平台仍可查看已同步对象，并显示来源不可用及最后同步时间。

### 验收三：同步正确性

验证以下情况：

- 同一事件重复投递。
- 较旧事件晚于新事件到达。
- 同步中途失败和重启。
- 全量导入期间发生业务修改。
- 对象删除后的有效关系清理。
- 对账发现遗漏变更并修复当前投影。

提供可复现结果，不能只在文档中声明支持。

### 验收四：新增对象类型

接入预留的教室类型及其关系。

列出此次新增类型实际修改的文件，证明主要修改集中在定义、映射和适配模块，通用查询内核与通用前端没有增加教室专用分支。

### 验收五：来源追溯与可重建

抽查对象属性和关系，能够追溯到原记录及映射依据。

重建当前投影后，对象身份、当前属性和关系应与重建前一致，历史记录按明确策略保留。

### 验收六：原业务回归

原有业务入口、调课校验、事务和演示功能继续可用。

业务时钟变化后，“当前课程”“下一节课”等动态结果正确，不能只依赖数据变更事件更新。

## 八、实施约束与交付

沿用现有 Java / Spring Boot 和 Vue 技术栈。新增独立本体服务与数据库，提供 Docker Compose 一键启动。

首版可以采用 PostgreSQL 关系表、JSONB 和必要索引。范围集中在接入、建模、同步、查询、追溯和展示，不要求同时引入图数据库、搜索集群、复杂消息集群或完整权限治理平台。

第一版真实接通一个业务数据源，并设计清楚新增来源的适配接口。已实现能力与未来扩展项必须分别说明。

业务库迁移要适用于已有数据卷，不能依赖删除原业务数据重新初始化才能升级。保护现有数据和其他项目。

最终交付：

1. 完整可运行代码及 Docker Compose。
2. 原业务、本体服务、两个数据库及前端之间的架构说明。
3. 本体定义、来源映射和扩展接口的真实样例。
4. 全量导入、增量同步、失败恢复和重建说明。
5. 分开的原业务 API 与本体 API 契约。
6. 已执行的编译、集成测试和浏览器验收结果。
7. 一条可直接照做的演示路径：原业务修改 → 底座同步 → 对象及关系变化 → 历史与来源追溯。
8. 原业务为接入平台修改了哪些地方，以及未来接入其他 Java 系统、达梦数据库的适配清单。

最终汇报要明确哪些已经实现和验证，哪些仍有限制。不要用静态假数据、仅前端联动或固定学校页面代替上述闭环。

请完成实现、启动和验证后再交付，不要只返回架构方案。
