# 本体数据底座 · 交付说明

> 本文是增量改造的**交付总说明**：架构、本体模型如何驱动运行时、同步闭环、已实现与未实现、原业务改动清单、达梦/其他 Java 系统适配边界、演示路径与测试证据。
> 需求原文见 `00-原始需求.md`；PRD / 架构 / 契约 / 测试计划见 `01`–`05` 同名文档。

## 0. 一句话结论

在**不改动原业务库结构、不删数据卷、不改变原有接口与校验**的前提下，新增了独立的本体服务（`ontology-service` + 独立 PostgreSQL `ontologydb`）与独立的平台入口（`ontology-web`），把学校业务的 6 类来源表映射为 7 类业务对象 / 10 类关系，做到：**定义驱动运行时、事务 Outbox 增量同步、全量导入与增量衔接、对账、可重建投影、跨对象查询与关系探索、变化与影响追踪、来源追溯**。

学校只是第一个接入案例：新增「教室」类型时，只改了 3 份定义/映射文件 + 1 个 Provider + 1 份文档，通用内核与通用前端**零改动**（§6）。

```
└───────┬──────────────────────┘        └──────────────┬───────────────┘

        │ ②异步投递（1s 轮询，指数退避）                │

│  ├─ 语义内核：稳定 ID、条件 UPSERT、关系重算、影响面、变更历史        │
│  ├─ SPI：SourceAdapter / FieldMapping / RelationRule / Provider / Resolver │
│  ├─ 同步：全量导入（水位衔接）、事件消费（去重/乱序/删除）、兜底追赶  │
│  ├─ 运维：对账、重建、同步任务、错误日志、失败重试                    │
│  └─ 双数据源：本体库读写主池 + 业务库**只读**独立池（仅 SELECT）      │
└──────────────────────────────┬──────────────────────────────────────┘
                               ▼
                 本体库 ontologydb :55433（14 张 ont_* 表）
```

**三条不可颠倒的约束**（已写入 `AGENTS.md`）：

1. 业务库是唯一业务事实源；底座的对象/关系是**可重建的投影**。
2. 业务处理不得同步依赖本体服务；本体服务停止时原业务仍可完成合法修改。
3. 平台不提供"直接改投影"的写入口；业务操作跳转原业务、沿用原有校验。

## 3. 本体模型如何真正驱动运行时

### 3.1 定义文件（随服务打包，加载即强校验）

| 文件 | 内容 |
| --- | --- |
| `ontology-service/src/main/resources/ontology/model/object-types.yaml` | 7 类对象：`school` / `class` / `student` / `teacher` / `course` / `lessonSession` / `classroom`；每类含 `displayName`、属性（名称/类型/展示名/来源表达式）、`defaultTitle`、`listFields`、`searchableFields`、`filterFields`、派生属性与 Provider 引用、来源映射引用 |
| `.../model/relation-types.yaml` | 10 类关系：`student_in_class`、`class_head_teacher`、`class_in_school`、`teacher_in_school`、`classroom_in_school`、`session_of_class`、`session_of_course`、`session_taught_by`、`session_in_classroom`、`student_taught_by`；含起止类型、正/反向展示名、基数、生成规则、业务有效时间列 |
| `.../mapping/school-source.yaml` | 数据源 `school-panorama`、7 张来源表的对象映射与字段映射、外键/联表关系规则、Provider 注册（`providers`）与 Resolver 注册 |

加载时由 `ModelDefinitionLoader` 做**强校验**（未知类型引用、缺失映射、关系端点不存在、Provider 未注册等直接启动失败），并由 `MappingVersionRecorder` 记录**映射版本**（内容哈希，如 `school-panorama:c159e7192cb5`）；每次落库的对象/关系/来源引用/变更历史都带这个版本号，可回答"这条数据由哪个映射版本生成"。

### 3.2 运行时真的在用这些定义（可自查）

| 能力 | 由定义驱动的证据 |
| --- | --- |
| 对象列表/详情 | 类型清单来自 `/model/types`；列表列 = `listFields`；详情属性 = `attributes` 定义；标题 = `defaultTitle` 模板渲染 |
| 全局搜索 | 只搜 `searchableFields` 声明的字段（`school: code,name`；`student: code,name,studentNo`；`lessonSession: code,courseName,className,teacherName`…） |
| 筛选 | 只接受 `filterFields` |
| 关系与关系图 | 关系实例由 `relationRules`（FK/联表）在快照期生成；关系展示名来自 `relationTypes.displayName` |
| 来源追溯 | `/objects/{gid}.source` 含 `sourceId/sourceTable/sourcePk/sourceCode/sourceHash/mappingVersion` |
| 派生属性 | `derivedProperties` 指向 Provider（如 `classStudentCountProvider`、`classroomUsageProvider`），快照期计算并落库（`origin=DERIVED`） |
| 动态结果 | `dynamicResolvers` 指向 Resolver（`lessonStatusResolver`、`schoolLessonResolver`），查询期按 `queryTime` 实时算、**不落库**、附 `basis` 计算依据 |
| 新增类型 | 只改定义/映射 + 必要时加 Provider，通用内核零改动（§6） |

### 3.3 稳定身份与"不合并"原则

- 全局 ID：`gid:{sourceId}:{objectType}:{sourcePk}`（如 `gid:school-panorama:lessonSession:3`）。
- 来源主键与全局 ID 分离存储（`ont_object.source_pk` / `global_id`）。
- 不同数据源即使主键/名称相同也**不会**合并；不允许按名称做跨源归并。

### 3.4 三类"看起来一样"的字段被严格区分

| 类别 | 例子 | 落库 | 变化来源 |
| --- | --- | --- | --- |
| 来源直接存在 | `LS-003` 的 `teacherName`、`startTime` | 是（`origin=SOURCE`） | 业务库变更 → 事件 |
| 映射/计算得到 | `class.studentCount`、`classroom.sessionCount` | 是（`origin=DERIVED`） | 快照期由 Provider 计算 |
| 依赖查询时间 | `currentLesson`、`nextLesson`、`lessonStatus` | **否** | 查询期按 `queryTime` 实时计算，附 `basis` |

> 因此"下一节课"跨过上课边界后会变，即使数据库没有任何写入。

## 4. 数据同步闭环

### 4.1 全量导入（快照 + 增量衔接，不漏不重）

```
W0 = 业务库当前 system_revision          ← 先取水位
逐类型分页扫描 → 生成对象/关系/来源引用（稳定 ID + 映射版本）
条件 UPSERT：ON CONFLICT ... WHERE EXCLUDED.applied_revision >= 当前 applied_revision
W1 = 业务库当前 system_revision
恒执行 catchUp(W0)：把 W0 之后产生的事件补上            ← 导入期间的修改不遗漏、不被旧快照覆盖
```

- 入口：`POST /api/ontology/import/full`；进度：`GET /import/progress?taskId=`；失败重跑：`POST /import/retry`。
- 幂等验证：连续两次导入对象数不变、`global_id` 无重复、`relation_id` 无重复（§9）。
- 首次导入实测 95 对象 / 329 关系，耗时约 2 秒（500 条/页）。

### 4.2 增量同步（事务 Outbox）

```
业务事务 {
  UPDATE lesson_sessions ...;
  INSERT change_records ...;          -- 原业务变更日志
  UPDATE system_revision SET revision = revision + 1;
  INSERT outbox_events(event_id, revision, change_kind, payload, ...);
}  -- 同一本地事务，原子提交
      ↓ 异步（投递器 1s 轮询；本体侧另有 2s 兜底追赶）
POST /internal/events → 本体服务单事务 {
  去重（process_event）→ 版本比较（event.revision vs 对象 applied_revision）
  → 写对象/关系/来源引用/对象版本/变更历史/影响
  → 推进 snapshot_revision 与 lastSuccessSyncAt
} 提交成功后才 ACK
```

- 事件带 `event_id` 唯一 ID、`revision`、`change_kind`、前后状态或可还原信息。
- **去重**：`event_id` 主键 + `ont_processed_event` 去重表。
- **乱序**：条件 UPSERT 保证旧事件不覆盖新状态；旧事件回 `STALE` 且不落库、不写历史。
- **删除**：`changeKind=DELETE` → 墓碑化（`deleted=true`）+ 两端有效关系失效 + 可解释变化记录。
- **失败恢复**：指数退避 1→2→4…≤60s，8 次转 `DEAD`；`/admin/retry` 重放；`IN_FLIGHT` 30s 看门狗。
- **一致性**：一次业务变化对应的对象、关系、变更记录、影响、平台版本在同一本体库事务内提交。
- **不影响业务**：投递器只读 `outbox_events` 并用 JDK `HttpClient` 异步发送；本体服务不可用时业务照常提交，事件留在 `PENDING` 由重试兜底。

覆盖的写入口：单条调课、**批量调整**（`POST /api/schedule/batch-adjust`，单事务、逐条校验、任一冲突整体回滚、1 条批次事件）、演示时钟变更、`sync-today`、`reset`。

### 4.3 对账

`POST /api/ontology/reconcile`：以业务库当前值（经同一套映射）为真值，与投影逐字段/逐关系比对，输出 `FIELD_DIFF` / `MISSING` / `ORPHAN` 等差异并修复当前投影。

- 修复历史 `origin=RECONCILE`，`operator=null`、`businessTime=null`，原因明确写"对账修复"——**不伪造操作人、发生时间与中间过程**。
- 可重复执行：第二次对账无新增差异。

### 4.4 重建（只重建当前投影，变更历史全保留）

`POST /api/ontology/rebuild`：

```
TRUNCATE ont_object, ont_relation, ont_source_ref, ont_object_version   -- 仅这 4 张
按"快照 + 稳定 ID"重建 → bump ont_platform_revision → 追加 1 条 REBUILD 任务记录
保留：ont_change_history, ont_change_impact, ont_sync_task, ont_processed_event,
      ont_error_log, ont_reconcile_run, ont_model_def, ont_mapping_version,
      ont_data_source, ont_platform_revision
```

> 注意口径：**变更审计（`ont_change_history`/`ont_change_impact`）跨重建保留**；对象版本序列 `ont_object_version` 与投影一起重建（它是「当前对象的属性版本」，随投影失效），因此重建后不会保留重建前的历史属性版本。这是刻意取舍，不是遗漏。

实测重建前后 `globalId` 集合、当前属性、关系三元组完全一致，历史条数不减少（§9）。

## 5. 平台界面（中文，5 类页面）

| 页面 | 关键能力 |
| --- | --- |
| 全景总览 | 对象/关系规模、数据源状态（五态）、同步状态与两类时间、近期变化与影响摘要、全局搜索入口 |
| 通用对象探索器 | 类型列表由定义生成；列表列 = `listFields`；筛选/分页/保留查询上下文；点进通用详情 |
| 对象详情 | 当前属性（标 `SOURCE`/`DERIVED`、Provider/Resolver）、动态结果（含 `basis`）、正/反向关系、最近变化、来源系统/来源记录/映射版本、返回原业务入口 |
| 关系探索 | 关系列表 + 纯 SVG 关系图（1–2 层、节点上限、中心对象自身边优先）；**1 层 = 该对象自身的边，2 层 = 中心 ∪ 一跳邻居的边**，同一条关系按 `relationId` 只出现一次；每条关系可解释"来自哪个字段/联表规则"；失效边以虚线区分 |
| 变化与影响 | 属性前后差异、关系增加/解除、来源事件、业务时间 vs 处理时间；区分 `SELF_CHANGED` 与 `DERIVED_RELATED` 并给依据；新旧两侧均可查同一 `changeId` |
| 模型与接入管理 | 对象类型/属性/关系类型/数据源/映射与版本/Provider/Resolver；全量导入、对账、重建、同步任务、失败重试入口；五态区分「暂无业务数据/尚未接入/同步落后/同步失败/已同步」 |

刷新协议：`useRevisionPolling` 轮询 `/revision`，**所有已打开视角刷新成功后才 ACK 版本号**；任一视角失败不 ACK，下一轮自动重试（不会因提前记住新版本而永久停留旧数据）。

平台不提供任何"直接改投影"的写入口；详情页的"返回原业务对象/去调课"跳转到 `:5180`。

| `backend/.../service/BatchAdjustService.java` | 新增：批量调课（单事务、逐条复用 8 条校验、任一冲突整体回滚、1 条批次事件，上限 50） |
| `backend/src/main/resources/application.yml` | 修改：新增 `ontology.dispatch.*` 配置段（投递开关、间隔、批量、超时） |
| `db/init/03_outbox.sql` | 新增：`outbox_events` 表定义（幂等） |

### 8.3 在线编辑关系类型（增量，2026-11-16）

需求背景：本体元模型原本只有 YAML 三件套（`object-types.yaml` / `relation-types.yaml` / `mapping/school-source.yaml`）随服务打包、构造期强校验、运行期不可变，页面上只能只读查看。本节记录把「关系类型」做成可在线编辑的完整链路。

**能力**

| 操作 | 端点 | 说明 |
| --- | --- | --- |
| 新增关系类型 | `POST /api/ontology/model/relations` | 落到 overlay 草稿文件，立即做 8 组校验 |
| 编辑关系类型 | `PUT /api/ontology/model/relations/{id}` | 同上；`kind` 在 `FOREIGN_KEY`/`JOIN_RULE` 间切换时动态校验必填项 |
| 删除关系类型 | `DELETE /api/ontology/model/relations/{id}?force=` | 被映射引用时返回 409 `DELETE_BLOCKED_BY_MAPPING`（见下方限制） |
| 恢复基线 | `POST /api/ontology/model/relations/reset` | 删除 overlay，等效于回到打包基线 |
| 版本时间线 | `GET /api/ontology/model/versions` | 生效版本 / 草稿 / 历史版本的哈希、来源、操作人、备注、时间 |
| 应用到运行时 | `POST /api/ontology/model/relations/apply` | 乐观版本校验 → 202 → 自重启加载新定义 → 启动自愈重建投影 |

**关键机制**

1. **overlay 与基线双闸门**：classpath 基线非法 → 拒绝启动；overlay 非法 → 回退基线 + 写 `ont_error_log(phase=OVERLAY_FALLBACK)` + 坏文件改名 `.invalid.<ts>`，**不锁死服务**。
2. **原子写**：`FileChannel.tryLock()` 串行 + 临时文件 + `ATOMIC_MOVE`，备份保留最近 5 份。
3. **版本与署名**：`mappingVersion = sourceId + ":" + sha256(三份生效文本)[0..12]`。行上已有非 `system` 的人工署名时，后续启动/重建一律原样保留（`DefinitionVersionAttribution` 单一裁决点 + SQL `CASE WHEN` 兜底），避免「重启一次署名被刷成 system」。
4. **应用 = 受控自重启**：`ONTOLOGY_SELF_RESTART_ENABLED=true` 时返回 202 并在 800ms 后 `System.exit(0)`，由 compose `restart: unless-stopped` 拉起；未开启时降级返回 200 `pendingRestart`，只提示手动重启、绝不自杀。
5. **启动自愈**：`DefinitionActivationRunner(@Order 15)` 比对生效哈希，变化则登记新 ACTIVE 并在 `ApplicationReadyEvent` 后异步重建投影；顺序必须早于 `MappingVersionRecorder(@Order 20)`，否则永远读不到「上一轮真正生效的版本」。
6. **不能热替换的原因**：`ModelRegistry` 被 37 处构造注入且运行期不可变，因此在线编辑只能走「写 overlay + 受控重启」，而不是热更新单例。

**限制（如实标注）**

- **删除受映射约束**：基线 10 条关系全部被 `school-source.yaml` 的 `relationRules` 引用，`force=true` 也不会绕过——因为删掉后重建会抛「未注册的关系类型」并被 `loader.validate` 判为非法，下次启动回退基线、改动静默失效。要删必须先改映射文件。
- **一次只能编辑关系类型**：对象类型、属性、映射规则仍需改 YAML 后重启。
- **单实例假设**：孤儿任务清理（§12 第 12 条）与自重启都基于「compose 里只有一台 ontology-service」。多副本部署需要改成分布式锁 + 滚动重启。

## 10. 达梦 / 其他 Java 系统适配边界（**未测试、未实现**）

### 10.1 已抽象出的接入点

| 扩展点 | 作用 | 学校实现 |
| --- | --- | --- |
| `SourceAdapter` | 扫描来源表、按主键取一行、健康检查、当前水位 | `SchoolJdbcSourceAdapter`（PostgreSQL） |
| `FieldMapping` | 字段取值与简单转换（`LOOKUP_NAME` / 日期时间格式化等） | 5 个实现 |
| `RelationRule` | 由外键/联表生成关系实例 | `FkRelationRule` / `JoinRelationRule` |
| `DerivedPropertyProvider` | 快照期派生属性（可用只读查询与 `lookups`） | 5 个（学校/班级/教师/教室等） |
| `DynamicResolver` | 查询期动态结果（按 `queryTime`，必须给 `basis`） | 2 个（课程状态、当日课程） |

### 10.2 接达梦需要验证/改动的部分

1. **JDBC 驱动与方言**：引入 `DmJdbcDriver18`；`jdbc:dm://host:port/SCHEMA`；确认连接池只读设置（`setReadOnly`）在达梦上的实际语义。
2. **DDL 方言**：本体库 DDL 现为 PostgreSQL 语法（`JSONB`、`GIN`、`ON CONFLICT`、部分索引、`nextval`）。达梦需改写为 `CLOB`/`JSON` 存储 + 唯一索引 + `MERGE INTO` 等；**这是最大的工作量**，不是换驱动即可。
3. **条件 UPSERT**：现依赖 `ON CONFLICT ... WHERE EXCLUDED.applied_revision >= 当前` 做乱序保护；达梦需用 `MERGE INTO ... WHEN MATCHED AND ? >= applied_revision THEN UPDATE`，并验证并发语义。
4. **水位来源**：现用 `system_revision.revision`（单行单调递增）。达梦系统若无此机制，需提供等价水位（如序列 + 触发器，或基于时间戳 + 去重键）。
5. **标识符大小写与长度**：达梦默认大写折叠、`VARCHAR` 长度语义、`JSON` 函数差异（`->>` 等）。
6. **只读账号与最小权限**：需在达梦侧建立只读账号并验证只能 SELECT。
7. **事务隔离级别**：本体库单事务写入对象+关系+历史+版本，需验证达梦在默认隔离级别下的可见性与锁行为。
8. **时间类型与时区**：`TIMESTAMP` 精度、时区处理、`Asia/Shanghai` 解释需实测。

### 10.3 接其他 Java 业务系统（非达梦）

- 实现一个 `SourceAdapter`（或其等价端口）+ 一套 `object-types.yaml` / `relation-types.yaml` / `<source>-source.yaml`，注册 `sourceId`，即可接入；**通用内核与前端不需要改**。
- 若来源系统已有事件机制（Kafka/MQ/CDC），可替代 Outbox：只要事件能满足"唯一 ID + 版本/水位 + 可还原变化"，消费端沿用同一套去重与条件 UPSERT。
- 需额外验证：来源系统的全局版本语义（是否单调）、删除语义（硬删/软删）、字段类型映射、字符集与排序规则。
